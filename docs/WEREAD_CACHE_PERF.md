# 微信读书整本缓存提速：源码级梳理

对照基准：GitHub 发布版 `6ec1b45`（`metalio-s31-0.3.3-rc113-final`，完全未优化的原始固件）。
本文记录从该版到当前代码的全部改动、每项的技术原理与实测收益。

---

## 一、结论先行

同一本书（32 章、56 张图、16 个章节资源包共 15.37 MB），端到端耗时：

| 轮次 | 端到端 | 相比原版 | 这一轮的关键改动 |
|---|---|---|---|
| 原始固件 | 581.2s | — | 逐章 reader 页 + 逐张图单独请求 |
| 中间版 | 269.8s | 2.2x | 请求压缩、连接池 |
| 中间版 | 175.1s | 3.3x | 图片改按章 tar 资源包 |
| 中间版 | 139.1s | 4.2x | 射频接收档（动态 RX 64 槽） |
| 中间版 | 99.3s | 5.8x | 关闭 ps 复用、进度节流 |
| 中间版 | 96.7s | 6.0x | 收尾帧竞争修复 |
| **81.5s（当前基线档）** | **81.5s** | **7.1x** | **预取重叠** |

改造的本质只有一句话：**把「延迟受限」的请求塞进「带宽受限」的下载窗口里**。
原始实现里，这两类请求严格串行，链路在等待时全程空转。

---

## 二、七项优化逐条拆解

### 1. 请求压缩：`identity` → `gzip`
**位置**：`main/book/weread.c:828`

原始代码给所有请求写死 `Accept-Encoding: identity`，reader 页每次传 170 KB 原始 HTML，
服务端分片下发，单页耗时 30–58 秒。

改成 `chunk ? "gzip" : "identity"`——只对流式请求（reader 页、`e_0/e_1/e_3` 分片）启用压缩，
非流式（tar 资源包）保持明文，因为图片本身已是压缩格式，再 gzip 只增加 CPU。

**踩过的坑**：判断响应是否 gzip 时，最初查 `Content-Encoding` 头，一直拿到 0 值——
IDF 的 `esp_http_client_get_header()` 对头名**大小写敏感**，服务端发的是小写 `content-encoding`。
最终改为判定响应体首两字节的 gzip 魔数 `1f 8b`：

```c
ESP_LOGI("WEREAD", "reader body magic=%02x%02x gzip=%d declared=%lld", ...);   // weread.c:991
```

解压侧用 `inflateInit2(&gz_stream, 16 + MAX_WBITS)` 做流式解压（`weread.c:981`），
32 KB 解压窗口通过 `gz_alloc` 走 PSRAM（内部 RAM 要留给 Wi-Fi），
输出块 2048 字节——刚好对齐字段扫描窗口（512 + 2048），扫描 `psvts` 等字段不跨块丢字。

**效果**：reader 页 170 KB / 30–58s → 41 KB / 1.01s。

---

### 2. 图片改按章 tar 资源包
**位置**：`main/book/weread_epub.c:305`（`WR_IMG_TAR_LIMIT`）

原始实现逐张图发请求：32 章 × 约 2 张 / 章的场景下，一轮 60 次 TLS 往返，仅图片就 291 秒。

微信读书的章节页里其实带着一个 tar 资源包地址（三种形态：`//` 开头、`/` 开头、完整 URL）。
改成：一次 GET 拿整个 tar（上限 8 MB），就地解 POSIX tar（512 字节头 + 文件名），
按 basename 填进 12 个图片槽位（`WR_IMG_SLOTS`）。

**效果**：60 次请求 → 16 次（每章 1 次），吞吐 95.9 KB/s → 351.6 KB/s。

---

### 3. 预取重叠（最大单项收益）
**位置**：`main/book/weread_epub.c:133`（`prefetch_task`）、`:187`（`prefetch_arm`）、开关 `:41`

这一项来自对耗时结构的观察：

| 请求类型 | 数据量 | 耗时 | 性质 |
|---|---|---|---|
| tar 资源包 | 15.37 MB | 48.5s | **带宽受限** |
| reader 页 | 每章约 1.1 MB | 30.4s | 延迟受限（每章 1.4s 里大部分是等包） |
| `e_0/e_1/e_3` 分片 | 小 | 20.0s | 延迟受限 |

三类请求串行执行时，tar 下载期间链路是满的，但 reader 页与分片期间链路基本空转。
于是加一个常驻预取任务：主任务处理第 i 章时，提前把第 i+1 章的 reader 页和
分片抓下来；下一轮开头取回结果，**取不到就退回原来的串行路径**，不会因为预取失败中断整轮。

三个安全前提都逐条核对过：
- 连接池按 **host 分槽**：预取走 `weread.qq.com`，tar 走 `res.weread.qq.com`，不会互抢同一条连接
- `z_stream` 与滴流看门狗都是**请求内局部变量**，两条流互不干扰
- 任务栈 12 KB 放 **PSRAM**（`xTaskCreateWithCaps`），内部 RAM 只剩 43 KB，不能占用

**效果**：96.7s → 81.5s（−15.7%），31/32 章命中预取（第 1 章没有可重叠的前序）。
代价是 tar 吞吐从 347.6 掉到 324.6 KB/s（−6.6%），两条流争缓冲，但净收益仍是正的。

---

### 4. 射频接收档
**位置**：`components/read_pico_transfer/transfer_s31_radio_profile.h`（`transfer_s31_thrifty_sta_config`）

原始配置下，80 KB 以上的资源包吞吐会塌到 3 KB/s——接收缓冲周转不过来，TCP 按 1.5s RTO 退避。

最终档位三条：

```c
static_rx_buf_num  = 3
static_tx_buf_num  = 3
dynamic_rx_buf_num = 64      // 惰性分配、优先 PSRAM，初始化不占内部 RAM
ampdu_rx_enable    = false
```

两条关键理解：
- **真正的杠杆是动态 RX 64 槽**，不是 AMPDU。开 AMPDU + 6 槽静态 RX 实测反而退步
  （tar 277.2 KB/s、端到端 173.4s，对比 351.6 KB/s / 139.1s）
- **静态 TX 必须压到 3 槽**：驱动把静态 TX 池当**一整块连续 DMA** 申请，6 槽先吃光最大的那块，
  剩下的不够再建静态 RX，直接 `Expected to init 3 rx buffer, actual is 0` / `ESP_ERR_NO_MEM`。
  缓存会话纯下行，用不到 6 个 TX 槽

另外加了**连续 DMA 守卫**：内部 RAM 最大连续块 < 8 KB 时跳过 Wi-Fi 初始化。
阅读页的 37 面板缓冲会把它压到 3.5 KB，此时硬初始化会让驱动停在半初始化状态，
表现就是「连不上 Wi-Fi / 进安全模式」。

**效果**：351.6 KB/s，已超过 Mac 跑同一 URL 的 79–91 KB/s，链路吃满。

### 5. HTTP 连接池
**位置**：`main/book/weread.c:377`（`WR_HTTP_POOL_SLOTS`）、`:379`（`WR_POOL_IDLE_US`）

原始实现每个请求重新握手，一次 TLS 约 600 ms。改为 3 槽按 host 复用的长连接池，配互斥锁
（并发下载时槽位不能被别的线程抢走）。三条保护：

| 机制 | 常量 | 作用 |
|---|---|---|
| 空闲过期 | `WR_POOL_IDLE_US` = 20s | 服务端 30–75s 关 keep-alive，客户端要写进死 socket 等满超时才发现 |
| `Connection: close` | — | 服务端要求关连接的响应不回池 |
| 失败换新重试 | — | 非流式请求在复用连接上失败时清池重发一次（流式不重试，重放会让字段扫描器收到重复数据） |

**效果**：省掉每次 600 ms 握手；避免死 socket 白等 8–10 秒。
日志里 `HTTP retry on fresh connection` 就是这层在兜底——出现说明它救回了一轮。

---

### 6. 进度刷新（本次已回退）
**位置**：`main/apps/app_weread.c:56`（开关 `WR_PROGRESS_AREA`）

| 方式 | 波形 | 单次 | 反相闪屏 |
|---|---|---|---|
| 整屏 `APP_REDRAW_PAGE` | 48 帧 | 580–700ms | **有** |
| 局部 `MODE_DU` 差分 | 16–20 帧 | 约 100ms | 无 |

32 章的书按 5% 一档要刷 20 次：整屏合计 13.1s 面板时间，局部只要约 3s。
且整屏刷新会跟下载任务抢 CPU，实测有一次从 581ms 拖到 2517ms 并报 `UNDERRUN`。

**当前状态**：为回到 81.5 秒那版，`WR_PROGRESS_AREA` 设为 `0`（整屏 5% 节流）。
置 `1` 即启用局部刷新，是纯 UI 收益，不影响下载路径。

---

### 7. 收尾帧竞争与 on_tick 门控
**位置**：`main/apps/app_weread.c`（完成分支）、`main/app/app_loop.c`（`tick_gated` 告警）

问题现象：缓存其实已经跑完（`work done kind=2 ok=1`），屏幕却永久停在「正在缓存图文」。

原因：进度条 100% 那一帧和完成提示那一帧相隔仅 63 ms，两次整屏刷新挤在一起，
后一帧抢不到面板被丢弃。修法是**收尾那一格不画**，只由完成分支一次画出书架和提示。

同时给 `on_tick` 加了门控告警：它是唯一能自己发起重绘的通道，
`power_dialog_open / quick / feedback / menu / request_app` 任一为真就会挡住重绘，
以前**失败时没有任何输出**。现在被挡超 5 秒会打一行：

```
W APP: on_tick gated power=0 quick=0 quick_owned=0 feedback=1 menu=0 ...
```

## 三、81.5 秒那一轮的耗时构成

| 项目 | 数值 | 占比 |
|---|---|---|
| tar 资源包（16 次 / 15.37 MB） | 48.5s（324.6 KB/s） | 59.5% |
| reader 页（33 次，均值 920ms） | 30.4s | 已与 tar 重叠 |
| `e_0/e_1/e_3` 分片（98 次） | 20.0s | 已与 tar 重叠 |
| HTTP 串行时间合计 | 98.9s | — |
| **实际墙钟** | **81.5s** | 重叠回收 17.4s |
| 电纸屏刷新（22 次） | 15.6s | 19.1% |

注意 HTTP 工作量 98.9s 却只用 81.5s 走完——这就是预取重叠的量化体现。

## 四、配置开关表

| 宏 | 文件 | 0 | 1 | 当前 |
|---|---|---|---|---|
| `WR_PREFETCH_CHAPTER` | `weread_epub.c:41` | 串行下载 | **预取重叠** | **1** |
| `WR_PROGRESS_AREA` | `app_weread.c:56` | **整屏 5% 节流**（81.5s 那版） | 局部 DU 差分 | **0** |
| `WR_IMG_PARALLEL` | `weread_epub.c:314` | **串行** | 并行拉图 | **0** |

`WR_IMG_PARALLEL` 保持 0 是实测结论：并行 TLS 流会让吞吐掉 5–20 倍，
S31 的内部 RAM 不足以同时维持多条 TLS 会话的收发缓冲。

## 五、已否决的方向（避免重复试错）

| 方向 | 结果 | 数据 |
|---|---|---|
| 打开 AMPDU + 6 静态 RX | 退步 | tar 351.6 → 277.2 KB/s，端到端 139.1 → 173.4s |
| 并行 TLS 拉图 | 严重退步 | 吞吐掉 5–20 倍 |
| 复用真实 `ps` 跳过 reader 页 | 失败 | 服务端校验 `ps`，30 章只成功 2 次，被拒还要等 7.4s 超时 |
| 图片 CDN 缩放（`imageMogr2`） | 被拒 | CDN 返 499；且原图仅 320×319，无压缩空间 |
| 继续调射频参数 | 无空间 | 351.6 KB/s 已超 Mac 同 URL 的 79–91 KB/s |

## 六、还有空间的地方

81.5 秒里 **93 秒是串行 HTTP**，面板刷新 15.6 秒。剩下可动的是：

1. **面板时间**：开 `WR_PROGRESS_AREA=1`，约省 10 秒（已实现，未启用）
2. **单章失败容错**：现在单章 `result=0` 会让整本作废（实测 143 秒白跑）。
   改成「记录失败章节、其余照常完成」属于结构性改动，需要改 EPUB 打包的收尾逻辑
3. **图片缺失**：某章 `<img src>` 是 `../Images/...` 形式，按 basename 没匹配上 tar 包内容，
   退化成 URL 抓取后被拒，该章会少一张图（不影响整轮成功）
